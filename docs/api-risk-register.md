# API 风险登记

## P0 风险

### `POST /words/complete`

- 风险：此前未鉴权，可被匿名调用。
- 风险：此前会读取第一条配置，存在越权和错配。
- 风险：此前失败时静默回退 mock 数据，污染真实词库。
- 当前处理：已要求鉴权，按管理员配置解析，失败改为显式错误。
- 后续动作：配置模型要进一步收敛为单一有效配置。

### `GET /admin/ai-config` 与 `PUT /admin/ai-config`

- 风险：此前接口直接暴露原始配置结构，存在明文 API Key 下发。
- 当前处理：已改为脱敏返回，空值更新不覆盖已有密钥。
- 后续动作：补充审计日志和配置变更历史。

### `POST /review/start` / `POST /review/{word_id}/result`

- 风险：前端目前能拿到答案并自主提交分数，可信度不足。
- 当前处理：尚未完成根治。
- 后续动作：引入 review session 和服务端状态校验。

## P1 风险

### `POST /words/`

- 风险：此前允许空词条进入数据库。
- 当前处理：已要求英文或中文至少其一存在。
- 后续动作：进一步规范去重策略和结构化字段。

### `PUT /words/{word_id}`

- 风险：更新语义不清晰，部分字段会被意外覆盖或遗漏。
- 当前处理：已改为 `WordUpdate` 并按提交字段更新。
- 后续动作：拆分更明确的响应模型和编辑模型。

### `/admin/users/{user_id}`

- 风险：删除管理员缺少保护。
- 当前处理：已禁止删除当前管理员并要求至少保留一个管理员。
- 后续动作：补充关联数据处理策略和测试。

## P2 风险

### 页面路由

- 风险：旧 Jinja 页面与新 Next.js 页面并存期会增加维护成本。
- 当前处理：已建立新前端骨架，但仍保留旧页面用于过渡。
- 后续动作：明确切流顺序和下线时点。
